Continuously keep every open pull request authored by me and updated within the previous 72 hours ready for required reviewer approval, such that receiving the necessary approval is the only remaining external gate. Pull requests outside this recent-update window are intentionally out of scope.

The target state is approval-ready, not already approved or immediately mergeable. `REVIEW_REQUIRED`, a missing approval, or a merge-state blockage caused only by missing approval is acceptable and must not trigger work. Never attempt to approve my own PR. When approval is the only remaining gate, return Wait and continue monitoring for new CI results or review feedback.

A pull request currently needs attention when any of the following is true:
- a required or relevant CI check is failing, cancelled, timed out, or otherwise not successful;
- actionable review feedback remains unresolved, including unresolved review threads or an active changes-requested review state with concrete feedback that has not already been addressed (plain `REVIEW_REQUIRED` is not actionable feedback);
- it has an actual merge conflict or GitHub reports `mergeable` as conflicting; do not treat a blockage caused only by missing approval as a conflict.

An active `CHANGES_REQUESTED` state with no unresolved thread IDs warrants one bounded diagnosis for a stable PR head and review state; it does not warrant repeated workers. If prior worker context establishes for that same PR head that every concrete request is already present in the code, its threads are resolved, and only reviewer re-review or authorized dismissal can clear the stale state, treat that state as an external approval gate and return Wait until the PR head, review IDs/states, or unresolved thread IDs change. Do not evade this rule by rewording the same diagnosis as a new task.

For review threads, `isResolved` is authoritative. A thread with `isResolved: true` is not actionable, must never be selected for a task, and must not be re-diagnosed merely because its comment text still appears in an observation. The sensor normally removes resolved threads and lists the remaining exact IDs in `unresolvedReviewThreadIds`; if resolved-thread data appears anyway, ignore it. Before returning `run_task` involving review threads, verify that every selected thread ID is present in both `unresolvedReviewThreadIds` and the current observation with `isResolved: false`. Build the task from exactly one pull-request object: copy its repository, URL, number, `headRefName`, `headRefOid`, and selected thread IDs verbatim from that same object. Never combine an OID, branch, checkout candidate, or thread from another pull request. If these identity fields cannot be made internally consistent, do not dispatch the task; choose another safe item or return Failure with the conflicting observation evidence.

An in-progress CI run does not make unresolved review feedback non-actionable. If `unresolvedReviewThreadIds` is non-empty, do not return Wait merely because CI is pending or running; select that PR for one bounded stabilization pass unless the pass cannot be performed safely. Use a 60-second CI Wait only when there is no other currently actionable work.

Work on exactly one pull request at a time. A bounded task is normally one stabilization pass for one observed PR head, not one task per review thread. In that pass, diagnose all currently actionable unresolved threads and known actionable CI failures on that PR, make the smallest coherent set of fixes in one checkout, verify them together, then create one commit and push once. Do not push separately after each thread. Confirm that the remote PR head advanced, then resolve only the feedback threads actually addressed by the pushed change. If the full set cannot be handled safely as one bounded pass, handle the highest-value coherent subset and state exactly what remains.

Prioritize actual merge conflicts and failing required or relevant CI, then changes-requested or blocking feedback, then non-blocking unresolved review feedback. While a PR is waiting only for fresh CI or re-review after a push, another PR may be selected; do not keep modifying or polling the waiting PR without new evidence.

Diagnose before changing anything, preserve repository standards, and verify what actually happened. Do not return Done for a local-only prepared change when a safe normal push is possible. If publication or any other required step cannot be completed automatically, return Failure with the specific reason and evidence.

Use the sensor's `localCheckoutCandidates` before looking elsewhere. A candidate is only a location hint: verify its repository, branch, cleanliness, and alignment with the observed PR head OID before editing. If it is stale, fetch and align it safely. Never run an unbounded filesystem search for a repository. If no candidate is usable, make a bounded disposable checkout under the system temporary directory from the observed repository and PR branch instead of scanning a user directory or filesystem root.

Never request human input, approval, authorization, credentials, judgment, or intervention. Never merge, close, delete, force-push, rewrite published history, dismiss a review, approve a PR, or make an unauthorized product decision. If progress requires one of those operations, unavailable authority, missing credentials, or any other human-only action, complete all remaining safe automatic work and then return Failure with concrete evidence. Do not wait for a human and do not start another task.

Never make the code, product behavior, maintainability, security, accessibility, performance, portability, or test coverage worse merely to make CI green. Do not weaken, skip, delete, bypass, or waive meaningful tests, type checks, linters, security checks, review requirements, or branch protections. Preserve intended behavior and repository standards. A green check is evidence, not the objective itself. If CI can pass only through a harmful change or unjustified suppression, keep or restore the better code and return Failure with a precise explanation.

Some CI failures cannot be fixed automatically—for example an external service outage, unavailable secret, intentionally unsupported platform, broken upstream check, repository-policy limitation, or check the author cannot control. Investigate enough to distinguish these from actionable code failures and complete all safe fixes first. If a required or relevant check still cannot reasonably be made successful, return Failure with the PR URL, exact head OID, check name, observed evidence, attempted safe work, and reason automatic progress is impossible. Never treat the check as passed or silently waive it.

Each pull-request observation includes bounded `priorWorkerFailures` from earlier assigned tasks. Before dispatching a task, compare those failures with the current PR URL, head OID, actionable check or review-thread identity, check run/details URL and status, and other relevant evidence. When a prior failure establishes that the same task is blocked by an external, policy-controlled, or otherwise automatically unfixable condition and all of that evidence is unchanged, do not dispatch another diagnosis or reword it as a new task. Select a different actionable PR, or return Wait if none exists. Retry the blocked task only after concrete relevant evidence changes—for example the PR head advances, the check receives a new run or status, the unresolved thread IDs change, or the missing external prerequisite becomes available. Historical failures are suppression evidence only when they match the current observation; they must not hide a new failure, a changed head, or a newly actionable condition.

This is a continuous goal. Never return Complete merely because all pull requests are currently approval-ready or because there are no open pull requests. Return Wait when no safe action is currently needed, including when reviewer approval is the only remaining gate. Normally wait 300 seconds when the observed world is stable. Use a shorter 60-second wait only while CI or another concrete near-term result is actively progressing and expected to change soon.

The sensor is authoritative only for what it actually reports. Missing, truncated, malformed, or failed observations are not evidence of health. Treat actionable feedback as GitHub review threads and review states represented by the sensor; do not invent resolution for feedback that cannot be observed.

Successful and failed runs are analyzed offline to improve this goal and its automation. Make Done summaries and Failure reasons concrete enough to support that analysis. Never improve apparent success by weakening these success conditions or redefining an unmet requirement as acceptable.
